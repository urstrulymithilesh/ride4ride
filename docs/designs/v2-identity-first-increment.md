## Problem Statement

Students at a university coordinate carpools in a WhatsApp group. It works because the group is trusted, but it does not scale, has no search or filtering, and every post disappears into chat history. Ride4Ride rebuilds that dynamic as a city and airport scoped classifieds board: people post ride requests or offers, and negotiation happens directly between them. The platform does discovery and connection only, not payments, routing, dispatch, or vetting.

The v1 core loop is already built and pre-launch. This doc specs the v2 increment: identity, dollar offers, ride completion, and reputation.

## What Makes This Cool

The private offers list. Today a poster publishes and waits, or a rider browses and hopes. With offers, the post owner gets a private, comparable list of people who want the ride and what they would pay, visible only to them. That inverts the work: the poster stops searching and starts choosing. The WhatsApp original could never do this, and keeping offers private avoids the lowball bidding spiral that public bidding produces.

## Constraints

- Stack is fixed: Next.js + Supabase. No framework changes.
- The platform is a board, not a dispatcher. No payments, no routing, no vetting.
- Utility over polish. No graphics-heavy UI. Users are on mobile data and low-end devices.
- Free service, so per-user variable cost (SMS) must stay bounded.
- Pre-launch with zero users, which makes one-way doors cheap right now.

## Premises

1. **This is a v2 increment, not an MVP build.** Accepted. The core loop ships.
2. **Stale spec sections get deleted, not debated.** Accepted. V2 removed the old tech-direction and MVP lists.
3. **Phone + OTP replaces email auth.** Your call, defended with reasoning: city and airport scoping removes the campus-email rationale that justified `allowed_email_domains`, and SMS cost is bounded by a 10-OTP / 24h rolling limit.
4. **Single-sided ride completion.** Your call, defended with reasoning: one-tap exit simplicity was prioritized over closing the edge case, with abuse routed to the existing report/block system. Residual risk recorded in Open Questions.
5. **Structured `$` offers may read as a ride marketplace rather than classifieds.** HELD OPEN. Not resolved this session.

## Approaches Considered

### Approach A: Identity First (chosen)

Migrate auth to phone + OTP with username, DOB, session policy, and OTP rate limit. Then build offers, completion, and ratings on stable identity.

### Approach B: Loop First (rejected)

Build offers, completion, and ratings on current email auth, migrate later. Rejected because `username` does not exist in any migration and the offer display copy depends on it, so offer and profile surfaces would be built twice.

### Approach C: Evidence First (rejected)

Ship completion and ratings only, let chat behavior answer the `$` offer question. Rejected because it defers the sharpest feature in the product.

## Recommended Approach

**Approach A.** Two facts decide it.

First, a hard dependency: the offer display copy reads *"(username) wants to be your captain for $15."* `username` returns zero hits across all seven migrations. It does not exist, and it arrives with the identity migration. Offers cannot ship cleanly before identity.

Second, timing: the app is pre-launch with zero users, nothing checked off in `PRE_LAUNCH_CHECKLIST.md`, and no production deploy. An auth migration today needs no data migration, invalidates no sessions, and locks nobody out. That price only goes up.

## Open Questions

1. **Structured `$` offers vs free-text cost sharing.** Decide before building the offers table, because the schema encodes the answer.
2. **Session rule contradiction.** Spec says both "24 hours of inactivity" and "24 hours regardless of activity." Those are an idle timeout and an absolute timeout. Pick one.
3. **Rating taxonomy contradiction.** Two different tag lists exist for one feature. Merge them.
4. **"driving intoxicated" is a safety report, not a rating tag.** Aggregating a DUI allegation into a thumbs-down count buries it. Route it to `reports`.
5. **DOB has no stated purpose.** Name the use (age gate?) or drop the field. Unused PII is liability for a platform whose legal position is "we are just a board."
6. **Username policy is undefined.** Uniqueness, case handling, change policy, reserved words. It is public identity, shown in offer copy.
7. **Expiry mismatch.** Spec says a flat 7 days; code uses a caller-supplied `p_expires_at`. Reconcile.
8. **Phone is now both the auth identifier and the revealed contact.** Confirm the reveal flow cannot leak the auth phone before mutual consent.
9. **Single-sided completion has no ceiling on stat inflation.** Accepted for v1. Record the cheapest mitigation now (for example, only count a completion when the two parties exchanged N messages) so it stays a small change later rather than a redesign.

## Success Criteria

- A user signs up with phone + OTP, claims a username, and never sees an email field.
- A post owner sees a private list of offers and opens a chat from one, and an independently started chat with the same user resolves to that same thread.
- Either party can end a conversation, one can mark it completed, the count appears on the public profile split by role, and the rating prompt fires.
- `PRE_LAUNCH_CHECKLIST.md` is rewritten against phone auth and every item is green.
- SMS spend per user is bounded by the OTP limit and is observable.

## Distribution Plan
